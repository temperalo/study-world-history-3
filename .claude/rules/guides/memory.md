# Memory — что сохранять в auto-memory, что нет

Auto-memory живёт в `~/.claude/projects/<project-hash>/memory/` и автоматически доступна между сессиями. Это **persistent**, в отличие от plan-ов и tasks (которые живут в сессии).

## Что сохранять

| Тип | Описание | Пример (study-проект) |
|-----|----------|----------------------|
| **user** | Роль, цели, контекст, стиль учёбы | «user учится в режиме breadth, не любит длинную теорию — just-in-time минимум до практики» |
| **feedback** | Guidance — как учить в этом проекте | «не вываливать теорию — user поправил: дай один факт и сразу к сборке; раздулся в M3 → застряли» |
| **project** | Факты про обучение, не выводимые из файлов | «цель — собрать рабочий капстоун-проект к 2026-09-01; режим breadth, ритм ~2 сессии/нед» |
| **reference** | Где лежат внешние материалы / железо | «детали для практики по электронике → ящик на полке; курс-источник по Python → ссылка X» |

## Что НЕ сохранять

- **Метод обучения, режимы, структура модуля** — они в learning-method.md / conventions.md / `_template.md`.
- **Git history** — `git log` авторитетен.
- **Что пройдено / результаты практики** — они в `docs/journal.md`, `artifacts/`, статусах модулей.
- **Roadmap / порядок модулей** — это в `docs/roadmap.md`, не в памяти.
- **Состояние текущей сессии** — это для модуля/session-log.
- **Всё что уже в CLAUDE.md / learning-method.md**.

## Когда записывать

- **feedback**: пользователь поправил или одобрил необычный подход к учёбе. Обе ситуации важны — иначе память однобокая.
- **user**: узнали уровень/предпочтения по стилю учёбы (breadth vs depth, переносит ли длинную теорию, любит ли диалог).
- **project**: узнали про цель обучения, дедлайн капстоуна, режим, ритм.
- **reference**: пользователь упомянул внешний материал/курс/железо и его назначение.

## Формат записи

Два шага. **1.** Отдельный файл `~/.claude/projects/.../memory/<topic>.md`:

```markdown
---
name: theory just-in-time
description: learning style — no theory dumps, one fact then straight to practice
type: feedback
---

Не вываливать теорию заранее. Дать ровно один факт, нужный для следующего шага, и сразу к сборке. Глубину — в `docs/backlog.md`, не в модуль.

**Why:** в M3 (резонанс контура) выдал полстраницы теории до практики — user застрял и заскучал, поправил: «дай собрать, объяснишь по ходу».

**How to apply:** при проектировании/прохождении модуля держать §2 теории сжатой; раздулось → backlog-глубины. Объяснять на лету в `/go`, привязано к тому, что сейчас под руками.
```

**2.** Одна строка в `~/.claude/projects/.../memory/MEMORY.md`:

```markdown
- [Theory just-in-time](theory-just-in-time.md) — learning style: no theory dumps, build first
```

MEMORY.md — индекс, не memory. Всегда в контексте, обрезается после 200 строк. Каждая запись — одна строка до ~150 символов.

## Важные правила

- **Без дубликатов.** Перед записью — проверить, нет ли уже memory на эту тему.
- **Проверять актуальность.** Memory может устареть. Прежде чем применять — проверь, что модули / метод ещё соответствуют (стиль учёбы мог поменяться).
- **`feedback` всегда содержит "Why" и "How to apply"**. Без "why" правило нельзя применить к граничным случаям.

## Когда читать memory

- Когда пользователь ссылается на прошлый разговор.
- Когда пользователь явно просит «вспомни / проверь память».
- Когда задача связана с feedback/project памятью.
- Если пользователь сказал «не используй память» — не применяем, не цитируем, не сверяемся.
